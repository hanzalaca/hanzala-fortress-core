# Hanzalaomator v2 Vault On-Disk Format (normative)

Status: **frozen for V1** (the first public app release), pending the §14
decisions listed below. This document
describes, byte for byte, the v2 vault exactly as the Swift code in
`Sources/HanzalaomatorCore` writes it today. It is meant for independent
implementations (e.g. an Android app using libsodium) and for security
audit. Where this document and the code disagree, the code is the bug
report: open an issue, do not silently "fix" either side.

Reference material:

- Python reference implementation (written from this document only):
  `Scripts/vault_format_reference/`
- Known-answer vectors and a fixture vault produced by that implementation:
  `Tests/HanzalaomatorCoreTests/Fixtures/v2-format-vectors/`
- Swift test that opens the fixture and checks every vector:
  `Tests/HanzalaomatorCoreTests/V2FormatVectorsTests.swift`
- Kotlin reader for Android (`Android/vault-core`) and its test that
  opens the same fixture and checks every vector:
  `Android/vault-core/src/test/kotlin/com/hanzala/fortress/vault/V2FormatVectorsTest.kt`

Keywords MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

What is frozen:

| Section | Status |
|---------|--------|
| §1–§12 (layout, keys, envelope, names, pool objects, recovery, metadata, JSON, chunks, fixed capacity, constants) | **Frozen for V1** |
| §13 (order of writes when creating/importing) | Informative: crash-safety protocol, may change without a format bump as long as the resulting bytes follow §1–§12 |
| §14 (open questions) | Not normative |

Before release, the questions in §14 that could change bytes on disk (§14.1
password Unicode normalisation, §14.2 unauthenticated envelope fields, §14.4
the KDF algorithm default) must be settled by the
security review. Any change they cause follows the "changing the format"
rule: a new version number and new vectors, with v2 still readable.

Running the reference implementation:

```
cd Scripts/vault_format_reference
python3 generate_fixture.py            # rewrites the fixture deterministically
python3 open_vault.py --check-vectors  # opens it (password + recovery key) and checks every vector
python3 open_vault.py <vault> --password '...'   # or --recovery-key 'HZRK-...'
```

The fixture uses Argon2id ops 2 / 8 MiB so tests stay fast; Swift reads it
because readers honour the parameters stored in each slot (§4.1).

## 0. Changing the format

Every byte described here is frozen. Any change to a constant, a byte
layout, a context string, a JSON field (name, type, encoding or presence
rule), a padding rule or a cryptographic primitive is a format change and
MUST:

1. bump the relevant version number (the envelope `formatVersion`, the
   slot payload version, the pool-object magic/payload version, or the
   metadata/manifest/recovery-payload `formatVersion`);
2. come with new fixture vault + vectors generated by the reference
   implementation, keeping the old ones (readers keep opening old vaults);
3. update this document in the same change.

`V2FormatVectorsTests` exists to fail when any of this is skipped.

## 1. Conventions

- All multi-byte integers inside binary structures are **big-endian**.
- `||` is concatenation. `utf8(s)` is the UTF-8 encoding of `s` with no
  Unicode normalization and no terminator.
- `hex(b)` is lowercase hexadecimal, two characters per byte.
- `HKDF(ikm, info)` is HKDF-SHA256 (RFC 5869) with an **empty salt**
  (equivalent to a salt of 32 zero bytes), output length 32.
- `HMAC(key, msg)` is HMAC-SHA256, 32-byte output.
- UUID text forms:
  - `UUID_UPPER(u)`: 36 characters, uppercase hex, hyphenated
    (`8-4-4-4-12`). This is what Swift's `JSONEncoder` writes for `UUID`.
  - `UUID_LOWER(u)`: the same in lowercase. Used inside cryptographic
    bindings.
  Readers MUST accept either case when parsing a UUID from JSON.
- Libsodium primitives used (all via libsodium 1.0.18+ semantics):
  - `crypto_pwhash` with `crypto_pwhash_ALG_ARGON2ID13` (Argon2id v1.3);
  - `crypto_secretbox_easy` (XSalsa20-Poly1305, 24-byte nonce, 16-byte tag
    prefixed to the ciphertext);
  - `crypto_aead_xchacha20poly1305_ietf_encrypt` (XChaCha20-Poly1305-IETF,
    24-byte nonce, 16-byte tag appended).
- `crypto_secretstream` is **not** used by v2. (`StreamFormat` /
  `SecretStreamEngine`, magic `HZSTRM01`, belong to the v1 vault format
  only.)
- All randomness is from the platform CSPRNG (libsodium `randombytes_buf`).
  Master keys and recovery secrets are 32 random bytes (Swift obtains them
  via `crypto_secretstream_xchacha20poly1305_keygen`, which is
  `randombytes_buf(32)`).

## 2. Folder layout

A v2 vault is a directory (the *root*) containing exactly:

| Path | Content |
|------|---------|
| `vault.hanzala` | The public access envelope (JSON, §4). Regular file, at most 1 048 576 bytes. |
| `objects/` | The shared object pool: a directory of regular files. |
| `objects/<name>` | One pool object (§6). `<name>` is 64 lowercase hex characters (`[0-9a-f]{64}`, i.e. 32 bytes). |

Names are shared with v1 on purpose (`VaultLayout.headerName`,
`VaultLayout.objectsDirectoryName`). A v1 vault additionally has
`index.hanzala` and/or `.journal/`; a v2 writer MUST refuse to create a
vault in a root that contains any of `vault.hanzala`, `index.hanzala`,
`objects`, `.journal`.

Writers stage files beside their destination and rename them atomically.
Staging names are `<prefix><UUID_UPPER>.tmp` with prefixes
`.hanzala-v2-envelope-stage-` (root), `.hanzala-v2-metadata-stage-` and
`.hanzala-v2-stage-` (in `objects/`). Readers MUST ignore any other entry.
Readers MUST NOT enumerate `objects/`: every object is found by a name
derived from a key (§5) or listed in authenticated metadata (§8).

Symbolic links are not followed: the root, `objects` and every object
MUST be a real directory / regular file (opened with `O_NOFOLLOW`).

### 2.1 Format detection

Read `vault.hanzala` (≤ 1 MiB), parse it as JSON and read the integer
member `formatVersion`: `1` → v1 vault, `2` → v2 vault, anything else →
unsupported. Never route by trying a password (`VaultFormatDetector`).

## 3. Keys and derivation

```
masterKey            32 random bytes, one per access path (slot)
recoverySecret       32 random bytes, one per access path

namespaceKey   = HKDF(masterKey,      "hanzala/namespace/v2")
objectKey      = HKDF(masterKey,      "hanzala/pool-object/v2")
recoveryNSKey  = HKDF(recoverySecret, "hanzala/recovery-namespace/v2")
recoveryObjKey = HKDF(recoverySecret, "hanzala/pool-object/v2")
```

`DomainKeyPurpose` context strings (the HKDF `info`, ASCII):

| Purpose | info | Used by v2 |
|---------|------|-----------|
| `indexV1` | `hanzala/index/v1` | no (v1 only) |
| `objectV1` | `hanzala/object/v1` | no (v1 only) |
| `namespaceV2` | `hanzala/namespace/v2` | metadata anchor name, cover names |
| `recoveryNamespaceV2` | `hanzala/recovery-namespace/v2` | recovery anchor name |
| `poolObjectV2` | `hanzala/pool-object/v2` | AEAD key of every pool object |

`DomainKeyDeriver.derive` rejects input keys that are not exactly 32 bytes.

Note that a recovery anchor is sealed with `HKDF(recoverySecret,
"hanzala/pool-object/v2")`: the recovery secret plays the role of a master
key for the pool-object codec.

## 4. Public access envelope (`vault.hanzala`)

### 4.1 JSON

UTF-8 JSON object, written by `V2VaultBootstrapStore` with Swift
`JSONEncoder`, `outputFormatting = [.sortedKeys, .withoutEscapingSlashes]`,
`dateEncodingStrategy = .iso8601` (JSON rules: §9).

```json
{"accessSlots":[SLOT,SLOT],"createdAt":"2026-01-01T00:00:00Z","formatVersion":2,"vaultID":"UUID_UPPER"}
SLOT = {"kdf":{"algorithm":"argon2id13","memoryLimit":M,"operationsLimit":O,"salt":"<base64 16 bytes>"},"wrappedPayload":"<base64 110 bytes>"}
```

| Field | Type | Rule |
|-------|------|------|
| `formatVersion` | UInt32 | MUST be `2` (`DualAccessEnvelopeV2.formatVersion`). |
| `vaultID` | UUID | Public vault identity. |
| `createdAt` | ISO-8601 date | Informational, unauthenticated (see open questions). |
| `accessSlots` | array | MUST have exactly 2 elements (`fixedSlotCount`). |
| `kdf.algorithm` | string | MUST be `"argon2id13"`. |
| `kdf.salt` | base64 | MUST decode to 16 bytes (`crypto_pwhash_SALTBYTES`). Fresh per slot. |
| `kdf.operationsLimit` | UInt64 | `0 < O ≤ 4` (`crypto_pwhash_OPSLIMIT_SENSITIVE`). |
| `kdf.memoryLimit` | UInt64 | `0 < M ≤ 1 073 741 824` (`crypto_pwhash_MEMLIMIT_SENSITIVE`), bytes. |
| `wrappedPayload` | base64 | `nonce[24] || secretbox_easy(...)`, 24+70+16 = 110 bytes. |

Production writers use `crypto_pwhash_OPSLIMIT_MODERATE = 3` and
`crypto_pwhash_MEMLIMIT_MODERATE = 268 435 456` (256 MiB). Readers accept
any parameters in the ranges above (libsodium additionally requires
`O ≥ 1`, `M ≥ 8192`). Readers MUST use the parameters stored in the slot.

### 4.2 Password → slot key

```
slotKey = crypto_pwhash(outlen = 32, passwd = utf8(password), salt,
                        opslimit = O, memlimit = M, alg = ARGON2ID13)
```

The password is the exact UTF-8 of the string as typed; no trimming, no
normalization (see open questions).

### 4.3 Slot payload (70 bytes, inside the secretbox)

```
offset size
0      1    payloadVersion = 0x02
1      1    role: 0x01 visible, 0x02 concealed
2      36   utf8(UUID_LOWER(vaultID))
38     32   masterKey
```

```
nonce          = random 24 bytes
wrappedPayload = nonce || crypto_secretbox_easy(payload, nonce, slotKey)
```

### 4.4 Unlock

For **every** slot (never stop at the first success): derive `slotKey`,
`secretbox_open_easy`; on success require length 70, byte 0 = 2, byte 1 ∈
{1,2}, bytes 2..37 parse as a UUID equal to the envelope `vaultID`
(compared as UUID values) and 32 key bytes. Exactly one slot must succeed;
zero → wrong password, two → ambiguous (error). Any per-slot failure
(KDF parameters out of range, auth failure, bad payload) counts as "did not
match".

### 4.5 Slot usage

- Slot 0 is always the visible access path; slot 1 is the concealed path
  or, in a visible-only vault, a dummy. Roles are taken from the decrypted
  payload, not from position.
- Dummy slot: password = standard base64 of 32 random bytes (discarded),
  random master key, role byte `0x02`. Its metadata anchor and recovery
  anchor are written like real ones (§7, §8), then all its secrets are
  discarded.
- Changing the visible password rewrites only slot 0 with a fresh salt and
  nonce; the master key does not change.

## 5. Derived object names

All names are `hex(HMAC(...))`, 64 lowercase hex characters.

| Object | Name |
|--------|------|
| Metadata anchor of an access path | `hex(HMAC(namespaceKey, "hanzala/v2/index-anchor"))` |
| Recovery anchor | `hex(HMAC(recoveryNSKey, "hanzala/v2/recovery-anchor" || 0x00 || utf8(UUID_LOWER(vaultID))))` |
| Fixed-capacity cover for bucket `b`, slot `i` | `hex(HMAC(namespaceKey, "hanzala/v2/cover-slot" || 0x00 || u64be(b) || u64be(i)))` |
| Any other object (data, chunk, manifest) | 32 random bytes, hex (`V2OpaqueObjectName.generate`) |

Labels are ASCII without terminator. `b` is the bucket plaintext size in
bytes (e.g. 4096), `i` the zero-based slot index in that bucket.

## 6. Pool object envelope (`HZOBJ003`)

Every file in `objects/` (metadata, data, chunk, manifest, recovery anchor,
padding/cover) has the same public shape (`V2PoolObjectCodec`):

```
file      = magic[8] || nonce[24] || ciphertext_with_tag
magic     = "HZOBJ003"  (48 5A 4F 42 4A 30 30 33)
AD        = magic || 0x00 || utf8(objectName)          (objectName = the 64-hex filename)
key       = HKDF(K, "hanzala/pool-object/v2")          (K = masterKey, or recoverySecret for recovery anchors)
ciphertext_with_tag = crypto_aead_xchacha20poly1305_ietf_encrypt(plaintext, AD, nonce, key)
```

Authenticated plaintext:

```
offset size
0      1    payloadVersion = 0x01
1      1    kind
2      8    logicalLength L (UInt64 big-endian)
10     L    content
10+L   P    padding: P random bytes (not checked by readers)
```

`kind`: `1` metadata, `2` data, `3` padding (cover), `4` chunk manifest,
`5` recovery anchor.

Sizes: `encryptedPayloadHeaderByteCount = 10`; the plaintext (header +
content + padding) is at most `16 777 216` bytes; file size is
`plaintext + 48`; so `58 ≤ file size ≤ 16 777 264`.

Reader MUST: check size bounds and magic; decrypt with `AD` built from the
name it opened (a ciphertext moved to another name fails); require
plaintext ≥ 10 bytes, payloadVersion 1, a known kind, and
`L ≤ plaintext length − 10`; return `(kind, content)`. Readers MUST then
check the kind expected by context (e.g. a metadata anchor must be kind 1).

### 6.1 Padding targets ("buckets")

The plaintext size (header + content + padding) is always one of:

```
4096, 16384, 65536, 262144, 1048576, 4194304, 16777216
```

- **Data object** (`V2DataObjectPaddingPolicy`): smallest bucket ≥
  `10 + contentLength`. Max single-object content is `16 777 206` bytes.
- **Metadata anchor** (`V2AccessMetadataPaddingPolicy`): smallest bucket ≥
  `10 + len(metadataJSON)`; in a fixed-capacity access path always exactly
  `1 048 576` (`V2FixedCapacityPlan.metadataPaddedPlaintextByteCount`),
  and metadata that would not fit is rejected ("vault full").
- **Chunk manifest**: same bucket rule as metadata (or the cover slot's
  bucket in a fixed-capacity vault).
- **Chunk**: always `4 194 304` (or its slot's bucket when fixed-capacity).
- **Recovery anchor**: always `4096` (`V2RecoveryAnchorStore.paddedPlaintextByteCount`).
- **Cover** (kind 3, empty content): its bucket size.

## 7. Recovery key and recovery anchor

### 7.1 Display form (`RecoveryKeyEngine`)

```
"HZRK-" + 16 groups of 4 uppercase hex characters joined by "-"
```

e.g. `HZRK-0011-2233-…` (85 characters). The 64 hex characters are the 32
`recoverySecret` bytes in order.

Normalization of user input: uppercase; remove all whitespace, newlines
and `-`; MUST then start with `HZRK` followed by exactly 64 characters
`[0-9A-F]`; anything else is invalid. The secret is the hex-decoded body.

### 7.2 Recovery anchor object

Name: §5. Pool object kind `5`, sealed with `K = recoverySecret`, padded to
4096. Content is JSON (`JSONEncoder`, `[.sortedKeys, .withoutEscapingSlashes]`,
no dates):

```json
{"accessID":"UUID_UPPER","formatVersion":1,"masterKey":"<base64 32 bytes>","roleRawValue":1,"vaultID":"UUID_UPPER"}
```

Reader requires `formatVersion == 1`, `vaultID` equal to the envelope's,
a 32-byte `masterKey`, and `roleRawValue` ∈ {1, 2}. Then it opens the
metadata anchor (§8) with `masterKey` and requires
`metadata.accessID == accessID`. Every failure is reported as one generic
"invalid recovery key" error.

Bootstrap writes one recovery anchor per slot (slot 1's secret is
discarded in visible-only mode; its role byte is 2).

## 8. Access metadata (one per access path)

Metadata anchor name: §5. Pool object kind `1`, sealed with the access
path's `masterKey`. Content is JSON written by `V2AccessMetadataStore`
with `outputFormatting = [.sortedKeys]` (**slashes are escaped as `\/`**),
`dateEncodingStrategy = .iso8601`.

### 8.1 `V2AccessMetadata`

| Key | Type | Presence |
|-----|------|----------|
| `formatVersion` | UInt32, MUST be `1` | always |
| `accessID` | UUID | always |
| `generation` | UInt64 | always; +1 on every committed change; 0 when created |
| `entries` | [Entry] | always |
| `pendingImports` | [PendingImport] | always written; readers treat missing as `[]` |
| `pendingChunkImports` | [PendingChunkImport] | always written; missing → `[]` |
| `pendingRemovals` | [PendingRemoval] | always written; missing → `[]` |
| `tombstonedObjectNames` | [String] | always (legacy; empty in new vaults) |
| `budget` | Budget | always |
| `usage` | Usage | always |
| `fixedCapacity` | FixedCapacityState | **only** when fixed capacity is on (`encodeIfPresent`) |

`Entry` (`V2AccessEntry`, all keys always written; readers treat a missing
`auxiliaryObjectNames` as `[]`):

| Key | Type | Meaning |
|-----|------|---------|
| `id` | UUID | Entry identity (= the import transaction ID). |
| `opaqueObjectName` | String | Single-object file: the data object (kind 2). Chunked file: the manifest object (kind 4). |
| `auxiliaryObjectNames` | [String] | `[]` for a single-object file; the chunk names in order for a chunked file. |
| `originalName` | String | File name (non-empty; not `.`/`..`; no `/`, `\`, NUL). |
| `logicalByteCount` | UInt64 | Plaintext file length. |
| `createdAt` | Date | Import time. |

`PendingImport`: `transactionID` UUID, `opaqueObjectName`, `originalName`,
`logicalByteCount`, `createdAt`, `coverSlot` (CoverSlot, only when
fixed-capacity).

`PendingChunkImport`: `transactionID`, `manifestObjectName`,
`originalName`, `logicalByteCount`, `chunks` ([{`opaqueObjectName`,
`logicalByteCount`}]), `sha256Digest` (base64, 32 bytes), `createdAt`,
`coverSlots` ([CoverSlot], only when fixed-capacity; manifest first then
chunks).

`PendingRemoval`: `transactionID`, `entryID`, `opaqueObjectName`,
`auxiliaryObjectNames` (always written; missing → `[]`),
`logicalByteCount`, `createdAt`, `coverSlots` (only when fixed-capacity).

`Budget` (`V2StorageBudget`): `totalBytes`, `reserveBytes`,
`safetyMarginBytes` (UInt64). Constraint: `totalBytes > 0`,
`reserveBytes < totalBytes`, `safetyMarginBytes ≤ totalBytes − reserveBytes`.

`Usage` (`V2LogicalUsageLedger`): `logicalBytes`, `objectCount` (UInt64).

`FixedCapacityState`: `capacityBytes` (UInt64), `isFilled` (Bool),
`ledger` = {`buckets`: [{`plaintextByteCount` Int, `slotCount` Int,
`coverBitmap` base64}]}. Bit `i` of the bitmap (byte `i/8`, mask
`1 << (i%8)`) set = slot `i` holds a free cover. `CoverSlot` =
{`bucketPlaintextByteCount` Int, `index` Int}.

### 8.2 Validation readers MUST apply (`V2AccessMetadata.validate`)

- `formatVersion == 1`; entry IDs unique; every object name valid 64-hex;
  no name owned twice across entries, pending imports, pending chunk
  imports, pending removals and tombstones (with the conflict rules in the
  code);
- `usage.logicalBytes == Σ entries.logicalByteCount`,
  `usage.objectCount == entries.count`;
- `usage.logicalBytes + Σ pending imports + Σ pending removals ≤
  totalBytes − reserveBytes − safetyMarginBytes`;
- pending chunk imports carry a valid manifest (§10);
- fixed-capacity consistency (ledger matches the plan of §11, covers +
  owned objects = slot count, pending transactions reserve distinct
  non-free slots; no cover slots at all when fixed capacity is off).

### 8.3 Reading a file

1. Unlock (§4.4) or recover (§7) → `masterKey`.
2. Read and validate metadata.
3. A session with pending work completes or aborts it first (crash
   recovery); a read-only reader SHOULD refuse or ignore pending items and
   list only `entries`.
4. Single-object entry: open `opaqueObjectName`, require kind 2 and
   `len(content) == logicalByteCount`.
5. Chunked entry: open the manifest (kind 4, §10), require
   `fileID == entry.id`, equal `logicalByteCount`, and chunk names equal to
   `auxiliaryObjectNames` in order; then open each chunk (kind 2, content
   length = its manifest length). A whole-file read verifies SHA-256 of the
   plaintext against the manifest digest (Swift's ranged reads do not).

## 9. JSON encoding rules (all JSON in this format)

Produced by Swift Foundation `JSONEncoder`:

- Compact: no whitespace, separators `,` and `:`; no trailing newline.
- Keys sorted. All keys are ASCII; byte-wise ordinal order is the required
  order (it coincides with Foundation's ordering for every key set here).
- Integers as plain decimal. Booleans `true`/`false`.
- `Data` → standard base64 (RFC 4648 §4) with `=` padding, no line breaks.
- `UUID` → `UUID_UPPER`.
- `Date` → `.iso8601`: `YYYY-MM-DDTHH:MM:SSZ` in UTC, whole seconds, no
  fraction (fractional seconds are dropped on write; a reader using
  Swift's `.iso8601` strategy rejects fractions).
- Strings: `"` and `\` escaped; control characters escaped (`\n`, `\r`,
  `\t`, `\b`, `\f`, otherwise `\u00XX` lowercase hex); non-ASCII written as
  raw UTF-8; `/` written as `\/` **only** in metadata (§8) — envelope,
  recovery payload and manifest use `.withoutEscapingSlashes`.
- Optional fields marked "only when" are omitted entirely when absent
  (never `null`).

Readers MUST accept any valid JSON with the same members (Swift ignores
unknown keys). Writers SHOULD produce the exact bytes above; the fixture
test checks that Swift re-encodes the Python-written envelope, metadata and
recovery payload to identical bytes.

## 10. Chunked files (`V2ChunkManifest`)

Used only when a file is larger than `16 777 206` bytes.

- Chunk content length: every chunk except the last is exactly
  `4 194 294` bytes (`4 MiB − 10`); the last is `1 … 4 194 294`. Each chunk
  is a kind-2 object padded to `4 194 304`. At least 2 and at most 16 384
  chunks.
- Manifest object: kind 4, random name (= entry `opaqueObjectName`),
  content JSON (`[.sortedKeys, .withoutEscapingSlashes]`):

```json
{"chunks":[{"logicalByteCount":4194294,"opaqueObjectName":"<64hex>"},...],"fileID":"UUID_UPPER","formatVersion":1,"logicalByteCount":N,"sha256Digest":"<base64 32 bytes>"}
```

  `formatVersion` MUST be 1; `fileID` = entry ID; `sha256Digest` = SHA-256
  of the whole plaintext; `logicalByteCount = Σ chunks > 16 777 206`;
  chunk names distinct and valid. Padding: smallest bucket ≥ 10 + JSON
  length.
- Entry: `opaqueObjectName` = manifest name, `auxiliaryObjectNames` = chunk
  names in order.

## 11. Fixed-capacity pools (optional per access path)

When enabled, the access path's pool is pre-filled with covers (kind 3,
empty content, padded to the bucket) at the derived names of §5, and
metadata gains `fixedCapacity`. Slot profile (`V2FixedCapacityPlan`) for
capacity `C` (`64 MiB ≤ C ≤ 256 GiB`):

```
for (bucket, percent, maxCount) in
   (4096,1,4096) (16384,1,2048) (65536,2,1024) (262144,4,512)
   (1048576,8,512) (16777216,16,unbounded):
     count[bucket] = min(C*percent/100/bucket, maxCount)      (integer division)
used = Σ count*bucket
count[4194304] += (C - used) / 4194304
```

Buckets with count 0 are dropped; the ledger lists buckets smallest first.
Real objects replace covers of the same bucket one for one; metadata is
always padded to 1 MiB. The fixture vault does not enable fixed capacity
(64 MiB minimum); cover naming is covered by vectors.

## 13. Creating a vault (reference order)

1. Two random master keys (slot 0 visible, slot 1 concealed or dummy); two
   slots (§4) with independent salts and nonces.
2. Create `objects/`.
3. For each slot: write empty metadata (`generation 0`, all lists empty,
   `usage` zero, the chosen budget) at its anchor name.
4. For each slot: a random recovery secret; write its recovery anchor
   (§7.2) with the metadata's `accessID` and the slot's role.
5. Re-read and authenticate all four objects.
6. Write `vault.hanzala` last.

Importing a single-object file (`V2OwnershipTransactionCoordinator`):
commit metadata with a `pendingImports` claim (generation +1), write the
data object at the claimed random name, commit metadata moving the claim to
`entries` with `id = transactionID`, `createdAt` copied, usage updated
(generation +1).

## 14. Open questions found while freezing

These are documented, not changed. Each needs a decision before or soon
after V1.

1. **Password normalization.** Passwords are hashed as raw UTF-8 with no
   Unicode normalization. A password typed on Android and macOS can differ
   in NFC/NFD form (e.g. accented letters) and then fail to unlock.
   Recommendation for the next version: NFC-normalize. Until then, Android
   MUST hash the exact bytes it has and users should be warned.
2. **Unauthenticated envelope fields.** `createdAt`, the slot order and the
   KDF parameters are not authenticated by anything except the fact that
   wrong parameters derive a wrong key. Swapping slots or editing
   `createdAt` is not detected. The slot payload binds only `vaultID`.
3. **No KDF lower bound on read.** Readers accept `operationsLimit ≥ 1`
   and any `memoryLimit` libsodium accepts. A slot can only be rewritten
   by someone holding the master key, so this is not a direct downgrade
   attack, but nothing flags a weak slot. The fixture uses ops 2 / 8 MiB
   on purpose.
4. **`KDFParameters` default.** `KDFParameters.init` defaults
   `algorithm` to `"argon2id"`, but `PasswordKeyEngine` only accepts
   `"argon2id13"`. Parameters built with the default can never unlock.
5. **Inconsistent slash escaping.** Metadata JSON escapes `/` (no
   `.withoutEscapingSlashes`); the envelope, recovery payload and manifest
   do not. Harmless today (no metadata string contains `/`, and base64 in
   metadata only appears in fixed-capacity bitmaps and pending chunk
   digests), but byte-exact writers must replicate it.
6. **Budget validation (resolved).** `V2StorageBudget` decoding now runs
   the same checks as its initializer: `totalBytes > 0`,
   `reserveBytes < totalBytes` and `safetyMarginBytes <= total − reserve`.
   A budget breaking them is rejected as malformed metadata. Readers in
   other languages MUST apply the same checks. No bytes on disk changed.
7. **UUID case.** JSON uses uppercase UUIDs, cryptographic bindings use
   lowercase; Swift's slot-payload check parses the UUID, so it would also
   accept an uppercase UUID inside the payload. Writers MUST use lowercase
   there.
8. **Recovery key and object key domain.** A recovery anchor uses the
   `hanzala/pool-object/v2` HKDF info under the recovery secret, the same
   label as ordinary objects under a master key. Separation relies on the
   two secrets being independent random values; a dedicated label would be
   cleaner in a future version.
9. **Padding bytes** inside the AEAD are random and never checked, so they
   are not a covert channel for an outsider but an insider can store data
   there.
10. **Date precision.** Dates lose sub-second precision on write; equality
    of in-memory metadata with re-read metadata depends on callers always
    re-reading (they do today).
11. **Chunking threshold.** Files of 16 777 207 bytes and more are chunked
    into 4 MiB chunks, while single objects go up to 16 MiB. A minimum
    chunked file therefore costs 5 × 4 MiB on disk. Not a bug; recorded
    because Android must reproduce the same threshold to keep vaults
    indistinguishable.
